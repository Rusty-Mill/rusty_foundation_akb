# Risk, assurance, step-up, and transaction binding

**RM-APP-AUTH-ASSURANCE-0001:** Assurance is an issuer- and policy-qualified conclusion over exact evidence, not a numeric property intrinsic to a factor. Reports name the framework/version, authenticator properties, ceremony protocol, identity proofing dependency, freshness, and exceptions.

**RM-APP-AUTH-ASSURANCE-0002:** Factor independence, phishing resistance, replay resistance, verifier binding, user presence, user verification, key exportability, hardware isolation, device binding, and transaction binding are separate properties.

**RM-APP-AUTH-ASSURANCE-0003:** Risk assessments bind versioned signals, sources, freshness, subject/account/session/device/channel/transaction context, model/rules generation, confidence/unknowns, privacy purpose, and decision. They are evidence, not authority.

**RM-APP-AUTH-ASSURANCE-0004:** Step-up creates a new transaction- or session-scoped ceremony plan and evidence generation. It preserves the requested action and amount/recipient/scope context and does not silently broaden the base session.

**RM-APP-AUTH-ASSURANCE-0005:** Transaction authorization cryptographically or otherwise verifiably binds the exact human-readable transaction where the selected protocol supports it. Generic authentication success does not prove approval of a different effect.

**RM-APP-AUTH-ASSURANCE-0006:** Changed risk, credential/session compromise, sensitive action, elapsed time, privilege elevation, recovery, or policy generation can require reauthentication, restriction, or revocation with accessible recovery paths.
