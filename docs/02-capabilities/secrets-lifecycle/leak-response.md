# Leak detection and incident response

**RM-SECRETS-LEAK-0001:** Detection inputs distinguish exact secret match in a protected scanner, provider/key identifier, structural candidate, entropy/pattern heuristic, commit/history/package/artifact/log/dump observation, target abuse, and third-party notification with confidence and provenance.

**RM-SECRETS-LEAK-0002:** Scanning minimizes disclosure, uses authorized bounded sources, isolates engines, protects candidate values and findings as secrets, avoids uncontrolled cloud submission, and does not persist reusable matches in reports.

**RM-SECRETS-LEAK-0003:** A response case binds suspected generations, targets/dependents, exposure locations/times/audiences, validation method, containment priority, revoke/rotate plan, artifact/history remediation, notification, forensic retention, and authority.

**RM-SECRETS-LEAK-0004:** Suspected compromise can immediately halt issue/use, revoke target credentials, rotate successors, invalidate sessions/tokens, quarantine artifacts, block publication/deployment, and increase observation under product incident policy.

**RM-SECRETS-LEAK-0005:** Removing a secret from the latest file does not remove repository history, caches, packages, logs, backups, forks, recipient copies, search indexes, or target validity; each is separately reconciled.

**RM-SECRETS-LEAK-0006:** Closure records confirmed or unconfirmed exposure, predecessor target denial, successor adoption, affected effects, residual copies, forensic holds, monitoring horizon, root cause, and preventive controls without claiming universal erasure.
