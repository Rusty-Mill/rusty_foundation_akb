# Namespaces, ownership, and succession

**RM-REPOSITORY-NAMESPACE-0001:** Namespace identity includes ecosystem/registry, canonical case/normalization, owner organization, creation generation, purpose, collision/confusability policy, and retirement/succession state. Source repository name, crate/package name, executable name, and capability identifier remain distinct.

**RM-REPOSITORY-NAMESPACE-0002:** Reservation requires evidence of project authority and intended use, applies anti-squatting/typosquatting/confusable review, and cannot imply endorsement or trademark ownership.

**RM-REPOSITORY-NAMESPACE-0003:** Package ownership is a revisioned role set with grantor, basis, scope, permissions, activation/expiry, identity provenance, approvals, and audit. Owners cannot silently grant broader organization or signing authority.

**RM-REPOSITORY-NAMESPACE-0004:** Ownership transfer uses an immutable proposal, old/new authority proof, package/repository/advisory review, waiting/notification window, quorum, credential rotation, and signed succession record. Transfer does not rewrite prior publisher evidence.

**RM-REPOSITORY-NAMESPACE-0005:** Abandoned, disputed, compromised, malicious, renamed, forked, and organization-dissolved namespaces enter explicit states. Reassignment preserves historical identity and requires exceptional governance; deletion cannot enable name/version resurrection attacks.

**RM-REPOSITORY-NAMESPACE-0006:** Dependency confusion defenses bind intended registry and namespace, source replacement policy, lockfile digest, and public/private precedence. An identically named package from another source is a different identity.

**RM-REPOSITORY-NAMESPACE-0007:** Organization and package owner inventories are periodically reviewed with minimum active quorum, recovery contacts, hardware-backed authentication policy, dormant-account handling, and succession drills.
